## Первопричина и доказательства

Первопричина — голодание Python-потока из-за тестового ожидания
`processEvents()` / `QTest.qWait(1)`. В измеренном PySide6 6.12.0 вызов
`qWait` удерживает GIL внутри C++; Python-реализации `QRunnable.run()` и
парсера тоже нужен GIL. Между короткими вызовами планировщик иногда даёт
worker достаточно времени, иногда — нет. Обработка GUI-событий сама по
себе не гарантирует прогресс фонового Python-кода.

Это дефект тестовой инфраструктуры, чувствительный к планированию потоков
на CI. Доказательств потери queued-сигналов или ошибки производственного
парсера в этих падениях не найдено. Простое увеличение времени ожидания
не устраняет механизм голодания.

Изучены оба требуемых неудачных запуска:

| GitHub Actions | Результат Ubuntu | Наблюдение |
| --- | --- | --- |
| [39191886079](https://github.com/Hazernit/operator-complex-python/actions/runs/39191886079) | 201/202, failures=1, skipped=0 | Большой импорт не завершился за 10 с |
| [39192006564](https://github.com/Hazernit/operator-complex-python/actions/runs/39192006564) | 199/202, failures=3, skipped=0 | Три маленьких импорта не завершились за 10 с; большой тест прошёл с пределом 45 с |

В обоих запусках установлены PySide6/Shiboken 6.12.0. Windows и macOS
прошли 202/202 без пропусков. Нестабильность маленьких файлов, чередующаяся
с успешным большим импортом, противоречит объяснению одним размером TXT.

Контролируемая диагностика на Ubuntu 24.04 ARM64, PySide6 6.12.0:

- GUI-таймер через 20 мс открывает `threading.Event`; QRunnable после него
  исполняет миллион Python-итераций. При `qWait(400)` worker начинает работу
  только после возврата ожидания, около 401 мс. При `QEventLoop.exec()` —
  около 25 мс, заканчивает около 51 мс.
- При исходном цикле `processEvents()` / `qWait(1)` worker начинает около
  133 мс и заканчивает около 432 мс. При таком же цикле с `time.sleep(0.001)`,
  который отпускает GIL, — около 21 и 46 мс.
- Четыре исходных теста с неизменённым парсером и одним доступным CPU:
  старое ожидание — 11.717 с, event loop — 0.549 с.
- В отдельном диагностическом опыте с одинаковым пределом **2 с** старое
  ожидание дало 3 passed / 1 failure на большом импорте; замена только
  ожидания дала 4/4 за 0.658 с. Этот уменьшенный предел применялся только
  в диагностике, не в тестах репозитория.

Исходные тесты с закоммиченными пределами времени локально также проходили;
точное падение CI с пределами 10/45 с в контейнере не воспроизведено.
Диагностика воспроизводит механизм и его влияние при одинаковой нагрузке.
Контейнер ARM64 отличается от GitHub runner x86_64; итоговые результаты
трёх ОС следует сверять с Actions исправляющего PR.

Документация Qt описывает [обработку событий в qWait](https://doc.qt.io/qt-6/qtest.html#qWait)
и [QEventLoop.exec](https://doc.qt.io/qtforpython-6/PySide6/QtCore/QEventLoop.html#PySide6.QtCore.QEventLoop.exec).
Вывод об удержании GIL основан на измерении Python binding 6.12.0,
а не на обещаниях документации C++ Qt.

## Проверка производственного кода

`RecordingLoader` оставлен без изменений:

- Парсер и расчёт границ `RecordingPlayer` выполняются в QThreadPool.
- `success`, `failure`, `finished` явно подключены через `QueuedConnection`
  к слотам loader в GUI-потоке; worker не обращается к QWidget.
- Qt автоматически удаляет C++ QRunnable после `run()`. `_jobs` удерживает
  Python wrapper и отдельный `_LoadSignals`, пока GUI не обработает `_finished`.
- Success/failure доставляется до finished. Выход из тестового ожидания
  должен проверять отсутствие pending jobs, а не только получение результата.
- Проверены 2000 быстрых запросов с принудительным GC без потери идентичности
  запросов и результатов. Отдельно проверено уничтожение QObject-владельца
  loader во время фонового разбора.

| Файл | Изменение |

| `tests/test_recording_loader.py` | Замена ожидания; проверка результата `waitForDone`, pending jobs и DeferredDelete; шесть регрессионных тестов |

| `scripts/ci_test_runner.py` | `--pattern`, положительный `--repeat`, свежий suite каждого повтора, длительность и общие счётчики; ошибка на skip/failure/error/пустом наборе |
| `.github/workflows/tests.yml` | Запуск PR в требуемую базовую ветку и 20 повторов RecordingLoader на Ubuntu; сохранена матрица трёх ОС |
| `docs/recording-loader-ci-investigation.md` | Этот отчёт |

Большой тест сохраняет **80 000 строк и 16 000 кадров**, настоящий парсер,
heartbeat GUI и проверки идентификаторов потоков. Предел ожидания уменьшен
с ранее добавленных 45 с до общих 10 с. Тесты не удалены, skip не добавлен.

Шесть новых регрессий проверяют:

1. Сохранение signals после auto-delete QRunnable до queued GUI completion.
2. Разрешение ожидающего worker настоящим GUI-таймером.
3. Возврат неуспеха по deadline, пока задача действительно ожидает.
4. Передачу исключения predicate через границу Qt callback в unittest.
5. Поток доставки failure от настоящего парсера.
6. Уничтожение QObject-владельца loader при ещё работающем парсере.

Адресный запуск `python -m unittest tests.test_recording_loader` и discovery
поддерживаются. Независимая проверка кода выявила и устранила возможное
поглощение исключения predicate внутри QTimer; соответствующая регрессия
исключает ложный успешный результат.

## Ограничения и риски

- Измерения относятся к PySide6 6.12.0 и указанным окружениям. Матрица CI
  и повторные тесты нужны при обновлении Qt/Python.
- Загрузка остаётся неотменяемой: закрытие владельца не прерывает парсер.
  Тест проверяет сохранность signals и отсутствие callback в уничтоженный
  receiver; он не доказывает все варианты завершения процесса во время работы.
  При уничтоженном владельце последнее освобождение signals может происходить
  из worker-потока — это существующий shutdown path, не причина данных падений.
- Никаких изменений алгоритма парсинга или рабочего поведения GUI не внесено.
  Изменения main, version/snapshot-веток, защиты репозитория и слияние PR
  не входят в исправление.
