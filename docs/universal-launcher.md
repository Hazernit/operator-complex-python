# Универсальный запускатель Python-проектов для Windows

Готовый файл: `output/run-python-project.bat`. Его можно передавать отдельно. В нём находятся только алгоритм подготовки и анализатор проекта; исходники приложения не включены.

Положите файл в корень уже распакованного Python-проекта. Откройте терминал в этой папке и выполните:

```powershell
.\run-python-project.bat
```

Команда подходит для CMD и PowerShell. Права администратора и ручная активация окружения обычно не требуются. Для загрузки Python и зависимостей нужен интернет. Поддерживается 64-битная Windows 10/11, x64 и ARM64.

## Что определяется автоматически

- `requirements.txt`: зависимости устанавливаются через Python из `.venv`.
- `pyproject.toml`, `setup.py`, пакетный `setup.cfg`: сам проект устанавливается через `pip install .`. Если есть и requirements, и пакетный манифест, применяются оба.
- `pyproject.toml`, содержащий только настройки инструментов, не вызывает установку текущей папки как пакета.
- `main.py`, `app.py`, `run.py`, корневой `__main__.py`, пакеты с `__main__.py` в корне или `src`, команды из `scripts` / `gui-scripts` метаданных пакета и Django `manage.py runserver` рассматриваются как способы запуска.
- Когда способ один, приложение запускается сразу. Когда способов несколько, предлагается меню. Например, у нашего проекта найдутся `main.py`, команда `operator-stub` и модуль `operator_stub`: для обычного запуска выберите `main.py`.
- Ограничения `requires-python`, `.python-version` и пользовательской настройки проверяются совместно. Существующая `.venv` тоже проходит эту проверку.
- Если `.venv` работает и подходит проекту, она используется повторно. Нерабочее или несовместимое окружение сохраняется в `.venv-backup-...`, затем создаётся новое. Отсутствующий pip восстанавливается в выбранной `.venv`.

Для анализа используется Python 3.11–3.14. Запускатель ищет установленные интерпретаторы и при необходимости скачивает проверенный установщик Python 3.13.16 или 3.14.8 с python.org. Если проект требует другую ветку или точную версию, например 3.12.4, она должна быть установлена заранее; при её отсутствии выводится объяснение. В `.python-version` поддерживается одна версия вида `3.12` или `3.12.4`.

Python устанавливается для текущего пользователя в `.runtime` проекта. Глобальный PATH не меняется. Переменная `PROJECT_PYTHON` позволяет добавить свой путь к интерпретатору; ограничения проекта продолжают действовать.

## Явная настройка необычного проекта

Если требуется зафиксировать точку входа или использовать другой файл зависимостей, создайте рядом необязательный `project-launcher.json`:

```json
{
  "python": "3.12",
  "requirements": "requirements/windows.txt",
  "install_project": false,
  "entry": {
    "type": "script",
    "target": "start.py",
    "args": ["--config", "config/demo.json"]
  }
}
```

Все поля необязательны. `requirements: null` отключает установку файла requirements. `install_project: false` отключает `pip install .`. Для `entry` поддерживаются обычный `.py`-скрипт (`script`), Python-модуль (`module`), установленная команда пакета (`console`) и его GUI-команда (`gui`). Аргументы передаются как список, без shell-интерпретации. Скрипт и файл requirements задаются относительно корня проекта.

Для Streamlit вместо обычного запуска `app.py` задайте модуль:

```json
{"entry": {"type": "module", "target": "streamlit", "args": ["run", "app.py"]}}
```

Для FastAPI с Uvicorn:

```json
{"entry": {"type": "module", "target": "uvicorn", "args": ["app:app", "--host", "127.0.0.1", "--port", "8000"]}}
```

Нужные пакеты должны быть объявлены в зависимостях проекта.

## Практические ограничения

Запускатель подготавливает локальное Python-приложение. Он не создаёт БД, не запускает Docker, не устанавливает драйверы оборудования или компиляторы и не заполняет секреты `.env`. Lock-файлы Poetry/uv/Pipenv не воспроизводятся их менеджерами: при пакетной установке pip использует ограничения манифеста. Зависящие от платформы библиотеки могут потребовать дополнительных действий, о которых сообщит pip.

Динамические зависимости и версия Python внутри исполняемого `setup.py` не извлекаются анализатором. Проверки самого установщика пакета продолжают действовать при `pip install .`. Зависимости не угадываются по названиям импортов.

Ошибки выводятся в терминал. Основной журнал — `python-project-launcher.log`, журнал установки Python — `python-project-install.log`. Окно остаётся открытым при ошибке.

## Разработка запускателя

Исходники: `scripts/windows_project_launcher.ps1` и `scripts/project_launcher.py`. Пересборка единственного передаваемого файла:

```bash
python3 scripts/build_project_launcher.py
```

Тесты анализатора и планирования запуска не требуют сети или подключённых роботов:

```bash
python3 -m unittest discover -s tests -p test_project_launcher.py
```

Алгоритм анализа и запуска проверяется на локальных тестовых проектах; выполнение оболочки Windows на macOS не проверяется.
