# Стандарт глубокого аудита репозитория (для следующих сессий)

**Проект:** [`Hazernit/operator-complex-python`](https://github.com/Hazernit/operator-complex-python)  
**Назначение:** неизменяемые принципы проверки проекта перед рекомендациями и после каждого изменения.  
**Уровень:** не менее глубокий, чем аудит README/CI 19.10.2026. Не принимать зелёный статус, красивый скриншот или утверждение README за доказательство работающей функции.

## 0. Как восстановить контекст

1. Прочитать **этот файл** и [план исправлений](IMPROVEMENT_BACKLOG.md). Затем `README.md`, `CONTRIBUTING.md`, `GITHUB_SETUP.md` и [техническое руководство](PROTOTYPE_GUIDE.md).
2. Проверить текущее состояние **на GitHub**, а не полагаться на старый SHA: `main`, ветки `version/*`, `feature/*`, теги `snapshot/*`, открытые PR, Issues, актуальный Ruleset и последние Actions.
3. Сверить цель с [планом подкоманды](../README.md#план-разработки): четыре направления — backend/контракт, адаптеры+Gazebo, dashboard, миссии/интеграция.
4. Если в чате нет истории решений, прочитать сохранённый чекпойнт ChatGPT Library `/Projects/operator-complex-python/TEAM_HANDOFF.md` (если доступен) и проверить данные заново.
5. При новых требованиях уточнить только **существенно недостающую** информацию, не выдумывать чужие логины, роли и выполнение задач.

## 1. Метод аудита: сначала факты, затем решения

Для каждого существенного вывода указывать **статус доказанности**:

- **Подтверждено** — непосредственная проверка текущих файлов, GitHub API, CI-лога, теста, скриншота или воспроизводимого запуска. Давать ссылку на ветку/коммит/путь/тест.
- **Вывод по коду** — следует из изученного фрагмента, но ещё не выполнено на нужной ОС/устройстве.
- **Гипотеза** — возможная причина или риск, требующий проверки.
- **Не проверено** — явно назвать ограничения среды. Отсутствие ошибок в логах ≠ успешная интеграция с реальными роботами.

Проверять факты по последнему `main` и точному SHA; отдельно отмечать устаревшие версии и особенности `snapshot/*`.

## 2. Обязательные области и конкретные вопросы

### Пользовательская ценность и UX

- Что пользователь реально может сделать за первые 3 минуты? Где заблокирован путь?
- Насколько понятны операции, пустые/ошибочные/offline/stale состояния, безопасность STOP, выбор платформ?
- Есть ли макеты/скриншоты для 1280×800, 1440×900, 1920×1080 и нативного DPI? Можно ли их воспроизвести?
- Совпадает ли экран с README, нет ли скрытых заглушек вместо функций? Дизайн оценивается как рабочий продукт, не только как внешний вид.
- Keyboard navigation, контраст, локализация, масштабирование и доступность: что проверено, что нет?

### Архитектура и контракты

- Проследить полный путь: источник → Adapter → контракт → backend → dashboard → команда → подтверждение/отказ.
- Где живая реализация, а где локальная модель/имитация? Не смешивать Qt-монолит, FastAPI, ROS 2 и Gazebo, если последних ещё нет в `main`.
- Проверить границы ответственности модулей, циклы, побочные эффекты, инварианты, обработку ошибок, таймауты, fallback.
- Для телеметрии: единицы, система координат, timestamp, freshness, `null` vs 0 vs offline, ownership данных.
- Для миссий: переходы состояний, безопасность команд, идемпотентность, повторы, отмена, потеря связи.

### Корректность, тесты, CI

- Воспроизвести команды README; читать **полный лог** workflow и причины skips/failures, а не только зелёный бейдж.
- Указывать по отдельности discovered, passed, skipped, failed, errors, платформу/версию Python.
- Если модуль GUI/Qt не импортировался и тест был пропущен, считать это **пробелом покрытия**, не прохождением теста.
- Проверять `PySide6`/`QtCore`/`QtWidgets`/`QtTest`, запуск Qt offscreen и smoke test; не заменять реальный GUI тест синтетическим выводом.
- Отличать unit, integration, GUI, smoke, Windows launcher shell, реальные hardware-in-loop проверки.
- Проверить кроссплатформенность и shell-специфику (`.bat`, PowerShell, macOS, Linux), воспроизводимость и нетривиальные граничные случаи.

### Безопасность и эксплуатация

- Не публиковать секреты, SSH-ключи, `.env`, `.venv`, логи, приватные данные/адреса настоящих роботов.
- Проверить `.gitignore`, ограничения зависимостей, безопасность скачивания установщиков, обработку путей и пользовательского ввода.
- Привилегии GitHub, Ruleset `main`, CODEOWNERS, PR, необходимые approvers; не обходить правила без поручения.
- Для физического оборудования отделять software STOP от подтверждённого hardware safety; анализировать безопасное состояние при offline.

### Документация и воспроизводимость

- Проверять каждую команду установки/запуска, наличие упомянутого файла, рабочие относительные ссылки и фактический путь артефакта.
- Сопоставить README, `pyproject.toml`, `requirements.txt`, скрипты, текущую структуру, версии и CI.
- При изменениях переносить длинные руководства в `docs/` **без потери содержимого**; README делать точкой входа.
- Обновлять дорожную карту по фактической реализации. Snapshot-теги — не релизы, пока явно не создан GitHub Release.
- Проверять public-facing About, badges, screenshot quality, license (если вопрос лицензии не решён — не выдумывать).

## 3. Как представить глубокий аудит

Представлять анализ в таком порядке (можно объединять разделы, не теряя смысла):

1. **Точный baseline:** репозиторий, SHA, дата проверки, что изучено, какая среда доступна.
2. **Что уже реально работает:** подтверждённые функции с ссылкой на код/тест.
3. **Что заявлено, но не подтверждено:** отдельный список без необоснованного оптимизма.
4. **Критические ошибки и блокеры:** риск, почему важно, воспроизведение, причина/гипотеза.
5. **Пробелы архитектуры, UI, документации, CI, безопасности:** конкретные примеры, не общие фразы.
6. **Решения:** альтернатива A/B, стоимость/сложность, совместимость и риски регрессии.
7. **Приоритеты P0/P1/P2 и зависимости:** owner, изменяемые файлы, DoD, точка интеграции, что можно делать параллельно.
8. **Результат:** что именно изменено и проверено, что осталось, следующий самый ценный шаг.

Без пользовательского запроса не обещать проценты качества, FPS, безопасную работу реального аппарата или полное покрытие тестами.

## 4. Протокол изменения репозитория

1. Сначала прочитать текущий файл и исходный SHA. Отдельная ветка `docs/*`, `fix/*` или `feature/*` от `main`; не переписывать `version/*`, `snapshot/*`.
2. Составить план с минимально достаточным набором изменений. Если радикальное улучшение README необходимо — **делать**, но не терять важную техдокументацию и не обещать недоказанное.
3. Проверять изменения по частям: Markdown-ссылки, синтаксис, тесты, smoke, workflow; PR с понятным diff и рисками.
4. Читать фактические результаты Actions после PR. `success` плюс `skipped > 0` — не равно полному успеху; красный CI честно диагностировать.
5. Проверить историю, что `main` не повреждён, снапшоты и Ruleset не изменены, затем объединить по разрешённому пользовательскому процессу.
6. **После каждого изменения** сообщать: файл/PR, мотив, проверку (команда, среда, число тестов), статус PASS/FAIL/SKIP/NOT RUN, ссылку, риск, следующий шаг. При длинной работе писать промежуточные подтверждённые итоги.
7. Обновлять [план исправлений](IMPROVEMENT_BACKLOG.md) с фактическим статусом и SHA/PR, не выдавать гипотезу за закрытую задачу.

## 5. Регрессии и запреты

- Нельзя считать 76 пропусков GUI-тестов «202 успешными тестами»; на исходном `main` 19.10.2026 был `Ran 202 tests`, `OK (skipped=76)`.
- Нельзя сливать историческую ветку `version/v0.3` в `main`: она возвращает прежний интерфейс.
- Не создавать GitHub Release, бинарный релиз, установщик или обещание поддержки Windows только из-за наличия `.bat`.
- Не раскрывать ФИО членов команды сверх необходимости; GitHub-логины назначать только после подтверждения.
- Не изменять правила доступа `main`, не снимать review/check requirements ради зелёной галочки.

> После очередного аудита проверяющий обязан скорректировать **факты и план**, а не автоматически переписывать этот стандарт под желаемый ответ.
